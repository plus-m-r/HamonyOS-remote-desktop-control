\section{需求分析}

\subsection{研究背景}
随着跨设备远程协助需求持续增长，用户对远程控制系统提出了更明确的期望，即在手机、平板与桌面端之间实现低门槛接入、低时延交互和可审计的会话过程。结合远程桌面市场扩张趋势与智能终端场景普及，本项目面向教育演示、家庭设备维护和中小团队技术支持，重点关注连接稳定性、操作流畅度与数据安全性。

\subsection{项目定位}

\subsubsection{面向用户}
本系统采用“原生HarmonyOS端+Flutter端+桌面端”的三端协同方案，服务远程办公人员、IT技术支持人员、远程教育工作者和系统管理员等群体，覆盖远程办公、技术支持、在线教学与服务器管理等典型场景。

\centering
\includegraphics[width=0.88\textwidth]{../reference/picture/目标用户与应用场景图.png}
\caption{目标用户与应用场景图}
\end{figure}

\subsubsection{主要功能}
系统围绕远程协助业务提供以下核心能力：
\begin{itemize}
	\item 跨网络设备连接与会话管理，支持连接状态回调与异常重连。
	\item 实时屏幕采集、传输与显示，支持增量更新与压缩传输。
	\item 远程输入控制，覆盖鼠标、键盘与触控等交互操作。
	\item 基础文件/信息交互，包括剪贴板同步与文件通道协同。
\end{itemize}

\subsubsection{主要性能}
系统在设计上强调低时延、高稳定和可扩展三项性能目标：通过分块增量传输与压缩策略降低带宽占用，通过心跳保活与自动重连提升会话连续性，通过分层接口与模块解耦提升功能扩展效率。下表给出与主流远控产品的技术对比。

\subsection{关键算法}

\subsubsection{屏幕捕获与增量更新算法}

\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{../reference/picture/屏幕捕获与增量更新算法图.png}
\caption{屏幕捕获与增量更新算法图}
\end{figure}

如图所示，屏幕捕获与增量更新算法采用分块捕获策略，将屏幕划分为固定大小的 tile，tile 尺寸由配置项控制，默认值为 $64\times64$ 像素。具体而言，给定屏幕尺寸 $(W_r,H_r)$ 和 tile 尺寸 $(W_t,H_t)$，首先计算网格维度 $x=\lceil W_r/W_t\rceil$、$y=\lceil H_r/H_t\rceil$，得到总 tile 数 $N_{total}=x\times y$。对于第 $k\in[0,N_{total}-1]$ 个 tile，其行列索引为 $i=\lfloor k/x\rfloor$、$j=k\bmod x$，左上角坐标为 $(x_{pos}^{(k)},y_{pos}^{(k)})=(j\cdot W_t,i\cdot H_t)$，实际尺寸为 $(w_{tile}^{(k)},h_{tile}^{(k)})=(\min(W_r-x_{pos}^{(k)},W_t),\min(H_r-y_{pos}^{(k)},H_t))$。每个 tile 独立捕获和处理，并通过 Adler32 校验和进行变化检测：计算当前帧校验和 $CS_{current}^{(k)}=Adler32(data_{tile}^{(k)})$ 并与上一帧 $CS_{previous}^{(k)}$ 比较，若不相等则标记为 dirty tile。所有 dirty tile 构成集合 $D=\{k\mid isDirty(k)=true,\,k\in[0,N_{total}-1]\}$，数量为 $N_{dirty}=|D|$。原始数据大小可表示为 $S_{raw}=\sum_{k\in D}(w_{tile}^{(k)}\cdot h_{tile}^{(k)}\cdot p)$（其中 $p$ 为每像素字节数，灰度图 $p=1$，彩色图 $p=4$），这与代码中按 dirty tile 统计有效载荷字节数的方式一致；经压缩后大小为 $S_{compressed}$，压缩比为 $\rho=S_{raw}/S_{compressed}$。该算法仅传输发生变化的 $N_{dirty}$ 个 tile 而非完整屏幕，带宽节省率可写为 $\eta=1-N_{dirty}/N_{total}$。在静态或低动态场景下，$N_{dirty}\ll N_{total}$，因此传输量会显著下降，结合 RLE+ZSTD 两级压缩可进一步降低网络负载，实现高效增量更新机制。

\subsubsection{异步处理与背压控制}
\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{../reference/picture/异步处理与背压控制图.png}
\caption{异步处理与背压控制图}
\end{figure}

如图所示，异步处理与背压控制机制以“任务队列 + 线程池 + 网络反馈”为主线展开。系统将远端数据输入拆分为捕获任务、控制任务和高优先级事件三类，其中鼠标等交互事件被赋予更高优先级，优先进入处理队列；普通捕获任务则按顺序排队，由线程池异步执行。设任务到达速率为 $\lambda$，处理速率为 $\mu$，队列长度为 $Q(t)$，队列上限为 $Q_{max}$，则当 $Q(t)/Q_{max}$ 超过阈值 $\phi_{high}$，或者网络状态监测结果表明链路拥塞时，系统触发背压控制，降低捕获频率或延后低优先级任务的执行；当 $Q(t)/Q_{max}$ 回落到阈值 $\phi_{low}$ 以下时，再逐步恢复正常处理速度。该机制与代码中的 `dataQueue`、`isProcessingData`、`maxDataQueueSize`、`captureWorkerCount`、`protocolWorkerCount` 以及心跳/重连策略相配合，使网络状态、队列积压和线程资源能够统一调度，从而避免任务堆积和界面卡顿。与此同时，动态重配置模块会根据运行态参数调整压缩配置和缓存策略，`TileCache` 也会在重置或参数变化时重建，保证处理链路在高负载条件下仍然保持稳定。该设计体现了“先保障交互，再平衡吞吐”的原则，适合远程控制这类对实时性敏感的场景。

\subsubsection{RLE + ZSTD 压缩算法}

\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{../reference/picture/RLE + ZSTD 压缩算法.png}
\caption{RLE + ZSTD 压缩算法}
\end{figure}

如图所示，系统采用三级压缩策略对 tile 数据进行逐层优化。设第 $k$ 个 tile 的像素矩阵为 $T^{(k)}\in\mathbb{R}^{h\times w}$（其中 $h$ 和 $w$ 分别表示 tile 的高度和宽度）。第一级为单色检测与优化：先判断当前 tile 是否为单色 tile，即 $isSingleLevel^{(k)}=true$ 且 $\forall i,j:T^{(k)}_{i,j}=c\,(c\in[0,255])$；若为单色，则编码为 $E_{1}^{(k)}=(type=single,value=c)$，此时数据大小仅为 1 字节，否则保留原始像素序列，数据大小为 $h\cdot w\cdot p$ 字节，其中 $p$ 为每像素字节数，灰度图 $p=1$、彩色图 $p=4$。第二级为 RLE 游程编码：对非单色 tile 的像素序列 $T^{(k)}_{i,j}$ 进行游程压缩，得到序列 $E_{2}^{(k)}=\{(v_{1},c_{1}),(v_{2},c_{2}),\ldots,(v_{m},c_{m})\}$，其中 $v_{l}\in[0,255]$ 表示像素值，$c_{l}\in\mathbb{N}^{+}$ 表示连续重复次数，且满足 $\sum_{l=1}^{m}c_{l}=h\cdot w$；该阶段的数据大小为 $S_{2}^{(k)}=2m$ 字节（假设每个 $(v,c)$ 对占 2 字节）。第三级为 ZSTD 压缩：将 RLE 编码后的数据进一步压缩，得到 $E_{3}^{(k)}=ZSTD\_Compress(E_{2}^{(k)},level)$，其中 $level$ 为压缩级别，默认值为 3，压缩后大小为 $S_{3}^{(k)}=|E_{3}^{(k)}|$ 字节。综合而言，对于第 $k$ 个 tile，最终编码结果为：若为单色 tile，则 $E^{(k)}=(marker=c)$；否则 $E^{(k)}=ZSTD\_Compress(RLE(T^{(k)}))$。所有 dirty tile 的总压缩数据为 $S_{compressed}=\sum_{k\in D}|E^{(k)}|+S_{metadata}$，其中 $S_{metadata}$ 为元数据开销，包含 frame ID、尺寸信息等；原始数据大小为 $S_{raw}=N_{dirty}\cdot h\cdot w\cdot p$（$D$ 为 dirty tile 集合，$N_{dirty}=|D|$ 为变化 tile 数量），压缩比为 $\rho=S_{raw}/S_{compressed}$，带宽节省率为 $\eta=1-1/\rho=1-S_{compressed}/S_{raw}$。三级压缩策略通过层层递进的优化，先在单色检测阶段消除冗余存储，再在 RLE 编码阶段利用空间局部性减少数据量，最后由 ZSTD 实现通用压缩，三者协同工作可获得较高的压缩比，并显著降低网络传输负载。

\section{安装及使用}

\subsection{环境要求}
\begin{itemize}
	\item JDK 8 及以上（项目 Maven 配置为 Java 1.8）。
	\item Maven 3.6 及以上（仓库内已提供可用 Maven 目录）。
	\item MySQL 5.7/8.0（服务端默认通过 JDBC 连接本地 MySQL）。
	\item HarmonyOS 开发环境（DevEco Studio + SDK，安装 HAP 用于真机/模拟器验证）。
\end{itemize}

\subsection{服务端部署}

\subsection{Java 客户端安装}
编辑 \texttt{client/config.properties}，按部署环境填写：
\begin{itemize}
	\item \texttt{serverIp}：服务端IP。
	\item \texttt{serverPort}：TCP端口（默认 \texttt{54321}）。
	\item \texttt{clipboardServer}：HTTP地址（示例：\texttt{http://<ip>:12345/remote-desktop-control}）。
	\item \texttt{robotPort}：机器人控制端口（默认 \texttt{49152}）。
\end{itemize}
随后运行客户端：
\begin{verbatim}
java -jar client/target/RemoteClient.jar
\end{verbatim}

\subsection{HarmonyOS 客户端安装}
使用 DevEco Studio 打开项目：

\centerline{\texttt{HarmonOS\_remote\_desktop\_control\_client}}

在配置文件中确认服务端配置：

\centerline{\texttt{entry/src/main/ets/config/ConfigCenter.ets}}

配置项如下：
\begin{itemize}
	\item \texttt{server.host}
	\item \texttt{server.tcpPort(54321)}
	\item \texttt{server.httpPort(12345)}
	\item \texttt{server.contextPath(/remote-desktop-control)}
\end{itemize}
完成后编译并安装 HAP 到设备，启动应用。

\subsection{使用流程}

\subsubsection{服务端启动}
在项目根目录执行构建，统一下载依赖并编译各模块：
\begin{verbatim}
mvn clean install -DskipTests
\end{verbatim}
修改 \texttt{server/src/main/resources/application.properties}，重点检查以下配置：
\begin{itemize}
	\item 数据库连接：
	\begin{itemize}
		\item \texttt{spring.datasource.url}
		\item \texttt{spring.datasource.username}
		\item \texttt{spring.datasource.password}
	\end{itemize}
	\item HTTP服务端口：\texttt{server.port=12345}，上下文：\texttt{/remote-desktop-control}。
	\item TCP控制端口：\texttt{netty.server.port=54321}。
\end{itemize}
启动服务端：
\begin{verbatim}
java -jar server/target/server-1.0.0.jar
\end{verbatim}
启动成功后，服务端会监听 HTTP（12345）与 TCP（54321）两条链路。

\subsubsection{客户端连接}
先启动服务端，再启动被控端客户端，最后启动控制端客户端，确保连接握手与设备发现稳定。

在客户端进入页中，左侧区域展示本机设备标识与连接密码；右侧输入目标设备ID和连接密码后发起连接。连接成功后进入远程画面，可进行鼠标、键盘与触控操作。

\subsubsection{功能操作说明}
\begin{itemize}
	\item 屏幕远程查看与控制：支持实时画面显示、点击、拖拽、滚轮等输入。
	\item 参数调整：可在会话中调整捕获与压缩参数（如帧率、压缩策略）。
	\item 剪贴板/文件协同：经 \texttt{clipboardServer} 对应 HTTP 通道完成文本与文件相关交互。
\end{itemize}

\subsection{常见问题解决}
\begin{itemize}
	\item 确保防火墙放通 \texttt{12345}（HTTP）和 \texttt{54321}（TCP）端口。
	\item 客户端与服务端必须使用一致的 IP、端口与上下文路径。
	\item 若出现连接超时，优先检查服务端日志、数据库连通性和网络可达性。
	\item Windows 锁屏场景下若需持续抓图，可按需启用 \texttt{robots} 模块配套方案。
\end{itemize}

通过上述流程，可完成从环境准备、部署启动到远程连接控制的完整闭环，满足本系统在教学演示、远程协助与运维支持场景下的实际使用需求。

\section{项目总结}
本项目围绕“连接稳定、交互低时延、链路可观测、部署可落地”四个目标，完成了 HarmonyOS 控制端、Java 服务端与桌面被控端的协同实现，并在统一协议下打通了屏幕流、控制流与剪贴板/文件协同通道。通过分块增量传输、变化检测、RLE+ZSTD 压缩、异步队列与背压控制等机制，系统在常见网络环境中实现了较好的实时性与稳定性；通过设备凭证校验、协议边界检查与日志审计字段补全，核心控制链路具备了基础安全能力和可追踪性。结合测试结果，当前版本已能够满足教学演示、远程协助与日常运维支持等典型场景的实际需求。

从工程实践角度看，本系统在架构上形成了较清晰的分层边界与模块职责：端侧聚焦交互与显示，服务端聚焦连接管理、协议处理与能力分发，业务扩展可在较小改动范围内完成；在交付上，项目已具备从环境准备、构建部署到联调验证的完整流程，能够支持快速复现与迭代优化。与此同时，针对弱网抖动、复杂动态画面和长时高负载场景，系统仍有进一步提升空间。

后续改进方向如下：
\begin{itemize}
\item \textbf{弱网自适应传输：} 引入更细粒度的自适应码率与动态帧率策略，结合链路实时状态自动调整 tile 与压缩参数，提升公网复杂网络下的连续性体验。
\item \textbf{编码与渲染优化：} 在保持画质可用的前提下探索差分编码、关键帧策略与渲染管线优化，降低高动态场景的带宽峰值与端侧开销。
\item \textbf{安全能力增强：} 完善传输加密、身份认证与会话权限分级机制，补充更细粒度的审计与告警能力，提升企业级合规适配度。
\item \textbf{可观测与运维体系：} 建立统一指标面板与异常追踪链路，增强故障定位、容量评估与版本回归效率。
\item \textbf{跨端一致性体验：} 持续推进 HarmonyOS 与 Flutter 端交互一致性建设，完善快捷操作与无障碍能力，降低不同终端间的学习成本。
\end{itemize}

总体而言，本项目已完成预期功能闭环并形成可持续演进的技术基础。后续将以“稳定性优先、安全性增强、体验持续优化”为主线，逐步向更高并发、更复杂网络条件与更广泛业务场景扩展。
